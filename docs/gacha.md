# Гача: баннеры, шансы, гарантии, дубли

Модуль `com.dating.gacha` (миграция `010-gacha.yaml`). В гаче в основном косметика и «чатовые» перки
(стикерпаки, обои чата), плюс расходники и дни премиума. Временные баннеры — под конкурсы и коллаборации.
Всё, что меняется по продуктовым причинам (баннеры, состав, веса, цены, гарантии), — **данные**, а не код;
экономические константы (осколки, курс обмена) — конфигурация с дефолтами.

## Модель

| Таблица | Что хранит |
|---|---|
| `gacha_banners` | `code`, `title`, `description`, `type` (`PERMANENT`/`LIMITED`), окно `starts_at`/`ends_at`, `active`, цена (`cost_item_code` = `GACHA_TICKET`, `cost_per_pull` = 1, `multi_pull_size` = 10), `pity_group`, правила гарантий (`epic_pity`, `legendary_pity`, `soft_pity_start`, `soft_pity_weight_step`), `sort_order`, `attributes` (JSON для клиентов: цвета, арт) |
| `gacha_pool_entries` | `(banner_code, entry_id)`: `reward_type` `ITEM`/`PREMIUM_DAYS`, `item_code` + `quantity` или `days`, `rarity`, `weight`, `featured`, `sort_order` |
| `gacha_pity_counters` | `(account_id, pity_group)`: круток с последней EPIC+, с последней LEGENDARY, всего |
| `gacha_pull_requests` | одна крутка ×1 или ×10: ключ идемпотентности клиента (уникален на аккаунт), баннер, количество, цена |
| `gacha_pulls` | история (append-only): аккаунт, баннер, группа, индекс в запросе, позиция пула, снимок награды, редкость, `result_type` `NEW`/`DUPLICATE_SHARDS`, осколки, причина гарантии, время |
| `gacha_test_forced_pulls` | очередь «следующие результаты» для тестовых аккаунтов |
| `catalog_items.GACHA_SHARD` | осколок удачи — обычный расходник (компенсация дублей) |

Кошелёк гача не трогает напрямую: билет списывается `EconomyService.spend`, награды выдаются
`EconomyService.grant(..., RewardSource.GACHA, ...)` — всё попадает в общий журнал экономики.

## Баннеры

- **PERMANENT** — всегда открыт (окно можно задать, но не обязательно). **LIMITED** — только в `[startsAt, endsAt)`.
- Время — `EconomyClock` аккаунта: тестовый аккаунт может «перемотать» время и увидеть окончание баннера.
- `active = false` выключает баннер без удаления (история хранит его код). Баннер с крутками удалить нельзя
  (`409 BANNER_HAS_PULLS`), только выключить.
- **Группа гарантий (`pity_group`)**: баннеры одной группы делят счётчики. Демо-лимитка в группе `LIMITED` —
  следующая лимитка с той же группой продолжит прогресс игрока (как «гарантия переносится» в больших играх).
  Постоянный баннер в своей группе `STANDARD`. По умолчанию группа = код баннера.
- Баннер без доступных позиций (пустой пул или все предметы выключены в каталоге) не показывается и не крутится.
- Не начавшийся баннер не виден (`404`), закончившийся виден по коду с `open: false` — чтобы шансы прошлых круток
  оставались доступны.

## Шансы и их раскрытие

Шанс обычной крутки = `вес позиции / сумма весов пула`. Ролл двухступенчатый: сначала редкость
(веса суммируются по редкости), затем позиция внутри редкости. Без гарантий это ровно та же вероятность,
зато гарантии и мягкая гарантия естественно работают на уровне редкостей.

API отдаёт (требование сторов и законов о «лутбоксах»):
- по редкостям: `weight`, `percent` (все 4 редкости, отсутствующая = 0);
- по каждой позиции: `weight`, `percent`;
- `totalWeight` — точная доля = `weight / totalWeight`;
- правила гарантий (`pityRules`) и личный прогресс (`myPity`).

Проценты — 4 знака, округление методом наибольшего остатка: **каждый список в сумме ровно 100.0000**
(проверяется тестами). Веса в демо-баннерах заданы в базисных пунктах (сумма 10 000), чтобы читались как проценты.

**Эффективные шансы с учётом гарантий выше базовых.** Гарантия EPIC+ сохраняет относительные веса EPIC и
LEGENDARY, поэтому каждая «гарантийная» крутка — это ещё и 1/6 шанса на LEGENDARY. Симуляция 5 млн круток
с демо-весами (70/24/5/1 %, EPIC+ за 10, LEGENDARY на 80):

| Редкость | Базовый шанс | Эффективный |
|---|---|---|
| COMMON | 70 % | ≈ 64,6 % |
| RARE | 24 % | ≈ 22,1 % |
| EPIC | 5 % | ≈ 10,7 % |
| LEGENDARY | 1 % | ≈ 2,6 % (в среднем 1 на ~39 круток) |

Это щедро, и это осознанный дефолт для демо. Если нужна более редкая легендарка — понизить её вес
(например, 50 из 10 000) или убрать LEGENDARY из гарантии EPIC+ (потребует флага в правилах).
Часть юрисдикций (Китай, Корея) требует публиковать именно эффективные («сводные») шансы —
см. «Дальше».

## Гарантии (pity)

Правила на баннере, счётчики — на аккаунт и группу:

- `epicPity = N` (по умолчанию 10): если `N − 1` круток подряд не было EPIC+, N-я крутка выбирается только среди
  EPIC и LEGENDARY (с их относительными весами). При N = 10 **каждая десятка содержит хотя бы одну EPIC+**.
- `legendaryPity = M` (по умолчанию 80): M-я крутка без LEGENDARY — гарантированно LEGENDARY.
- `softPityStart` + `softPityWeightStep` (выключено): начиная с крутки `softPityStart` без LEGENDARY вес
  редкости LEGENDARY растёт на `step × k` (k = 1, 2, …) в единицах весов пула. Целые числа — без потери точности.
- Счётчик сбрасывается, когда редкость выпала **любым способом** (сама или по гарантии); LEGENDARY сбрасывает оба.
- Гарантия редкости, которой нет в пуле, игнорируется. `0` в админке выключает гарантию.
- Счётчики меняются под блокировкой строки (`SELECT … FOR UPDATE`), см. «Конкурентность».

Свойства проверяются юнит-тестами на детерминированном генераторе (`GachaRollerTest`): максимум 9 круток без
EPIC+ и 79 без LEGENDARY на 20 000 круток для каждого из 5 сидов, точное срабатывание на пороге, сохранение
относительных весов, мягкая гарантия, соответствие частот раскрытым шансам на 200 000 круток.

## Крутка

`POST /gacha/banners/{code}/pull {count: 1 | multiPullSize, idempotencyKey}` — одна транзакция:

1. advisory-lock на аккаунт (все гача-операции аккаунта по очереди);
2. ключ уже был → вернуть сохранённые результаты (`replayed: true`), ничего не списывая; тот же ключ для другого
   баннера/количества → `409 IDEMPOTENCY_KEY_REUSED`;
3. баннер открыт по часам аккаунта, иначе `409 BANNER_NOT_ACTIVE`; количество 1 или размер мульти, иначе
   `400 INVALID_PULL_COUNT`;
4. запись запроса + `spend(cost)` с ключом `gacha:spend:<requestId>` → `409 INSUFFICIENT_BALANCE` откатывает всё;
5. блокировка счётчика гарантий, роллы по одному с `SecureRandom` на сервере;
6. дубли → осколки; один `grant` на весь запрос с ключом `gacha:<requestId>`;
7. сохранение счётчиков и истории; продуктовое событие `gacha_pulled` (без PII).

Цена мульти-крутки = `costPerPull × multiPullSize` (скидки нет — гарантия EPIC+ в десятке и есть бонус;
скидку можно добавить полем баннера). Ответ: результаты (награда, редкость, `isNew`, `outcome`, осколки,
причина гарантии), счётчики после крутки, остаток билетов и осколков.

### Конкурентность

- Перерасход невозможен: баланс билетов блокируется в `spend` (тест: 10 параллельных круток при 3 билетах →
  ровно 3 успешных, баланс 0).
- Счётчики гарантий блокируются построчно; дополнительно транзакционный advisory-lock на аккаунт, потому что
  проверка «косметика уже есть» должна быть последовательной и между баннерами разных групп.

## Дубли и осколки

- Дубль = не-стекаемая косметика, которая уже есть у аккаунта **или** уже выпала раньше в этом же запросе.
  Вместо предмета выдаются осколки `GACHA_SHARD` по редкости позиции: COMMON 1, RARE 5, EPIC 20, LEGENDARY 60.
- Расходники и дни премиума дублей не имеют — всегда начисляются (`outcome: NEW`, `isNew: true`).
- Обмен: `POST /gacha/shards/exchange {tickets, idempotencyKey}` — 30 осколков → 1 `GACHA_TICKET`,
  до 100 билетов за раз; повтор с тем же ключом ничего не меняет (`applied: false`).
- Оценка для «Стандартного» по эффективным шансам: когда вся косметика собрана, крутка в среднем даёт
  ≈ 4,6 осколка (COMMON ≈ 0,65 + RARE ≈ 0,7 + EPIC ≈ 1,7 + LEGENDARY ≈ 1,5), т.е. ≈ 15 % круток возвращается
  билетами; пока коллекция не собрана — меньше. Курс и ставки — в конфигурации.

## Админка

`GachaAdminService` — CRUD баннеров и позиций пула; REST под `/api/v1/admin/gacha/**`.
Проверки: код `A–Z0–9_`, у LIMITED обязательны начало и конец, цена — только расходник, у косметики количество 1
и редкость совпадает с каталогом (не указана → берётся из каталога), предмет существует. Каждое изменение
пишется в лог с id редактора.

**Временный доступ.** Порт `com.dating.common.security.AdminAccess#requireContentEditor`. До появления ролей
работает запасная реализация `com.dating.testing.TestAccountAdminAccessConfig`: тестовые аккаунты при
`app.testing.enabled=true`, остальным `403 ROLE_REQUIRED`. Она объявлена как
`@Bean @ConditionalOnMissingBean(AdminAccess.class)` — как только модуль ролей зарегистрирует свой
`AdminAccess` (`@Component`), запасная отключится сама.

## Тестирование

Для тестовых аккаунтов (`/api/v1/testing/gacha/*`, только при `app.testing.enabled=true`):

| Что нужно | Запрос |
|---|---|
| Состояние: очереди, счётчики, число круток | `GET /testing/gacha/state` |
| Следующие результаты баннера | `PUT /testing/gacha/banners/{code}/forced` `{"entryIds": ["frame_neon", "stickers_cats"]}` |
| Очистить очереди | `DELETE /testing/gacha/forced` |
| Поставить счётчики («79 без легендарки») | `PUT /testing/gacha/pity/{group}` `{"pullsSinceEpic": 0, "pullsSinceLegendary": 79}` |
| Сбросить все счётчики | `DELETE /testing/gacha/pity` |
| Очистить историю | `DELETE /testing/gacha/history` |
| Билеты / осколки | `POST /testing/wallet/items/GACHA_TICKET` `{"quantity": 10}` (то же для `GACHA_SHARD`) |
| Конец лимитки | `POST /testing/clock/advance` `{"days": 366}` |

Принудительный результат важнее гарантии, но счётчики двигаются по его редкости — так проверяется и гарантия:
9 принудительных COMMON → 10-я крутка гарантированно EPIC+. Очередь читается только при включённом testing.

## Решения

- **Двухступенчатый ролл** (редкость → позиция) вместо одного взвешенного выбора: та же базовая вероятность,
  но гарантии и мягкая гарантия выражаются точно и в целых числах.
- **Гарантии внутри одной транзакции со списанием**, счётчики в отдельной таблице по группе — лимитки могут
  делить прогресс, постоянный баннер — нет.
- **Дубль определяется гачей**, а не `grant`: иначе дубль был бы просто «0 в журнале», а нужна компенсация.
  Косметика выдаётся только если её нет; вместо дубля — осколки одной строкой `grant`.
- **Идемпотентность — своя таблица запросов** (а не только ключи экономики): повтор должен вернуть те же
  результаты, а не просто «ничего не делать». Неудачная попытка (нет билетов) не оставляет следа, ключ можно
  повторить после пополнения.
- **Снимок награды в истории** (`item_code`, `quantity`, `days`, `rarity`): история не меняется, если позже
  поменяли пул.
- **Не начавшийся баннер скрыт** (сюрприз конкурса), закончившийся — виден по коду.
- **Время баннера — по часам экономики аккаунта**, как премиум: тестировщик проверяет окончание лимитки без
  правки данных.
