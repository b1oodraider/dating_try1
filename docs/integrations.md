# Подключение SMS-шлюза и оплаты

Сейчас на сервере нет ни SMS, ни оплаты. Вход работает только для тестовых номеров (`APP_TESTING_*`),
купить ничего нельзя: премиум и расходники выдаются тест-панелью, достижениями, гачей и недельными начислениями.

Секреты провайдеров кладутся только в `/opt/dating/.env` на сервере, в git их не коммитим.
Переменные с префиксами `APP_SMS_` и `APP_PAYMENTS_` скрипт `infra/vps/install.sh` сам переносит в окружение
бэкенда. После правки `.env` перезапусти установку:

```bash
DOMAIN=instareject.ru bash /opt/dating/install.sh
```

---

## 1. SMS-шлюз (коды входа)

### Что уже есть

- Интерфейс `OtpSender` (`backend/.../auth/application/OtpSender.java`) с одним методом
  `send(phoneDigits, code)`. Номер приходит в виде цифр с кодом страны (`79001234567`).
- `AuthConfig.otpSender()` выбирает реализацию. Сейчас в проде это `UnavailableOtpSender`, который отвечает
  `503 OTP_DELIVERY_UNAVAILABLE`.
- Лимиты и защита уже сделаны в `AuthService`, отдельно их писать не нужно: срок жизни кода, число попыток,
  пауза между запросами, лимит в час и в сутки на номер. Номер хранится только в виде HMAC-хеша.

### Как подключить (на примере провайдера с HTTP API)

1. Создать класс в `auth/application`, например `SmsRuOtpSender implements OtpSender`:
   - запрос к API провайдера через `RestClient` с таймаутами примерно 5 секунд;
   - **код и полный номер не логировать**, в логах только маска и id сообщения от провайдера;
   - при ошибке провайдера бросать
     `ApiException.serviceUnavailable("OTP_DELIVERY_UNAVAILABLE", "Не удалось отправить код. Попробуйте позже")`,
     тогда клиент покажет понятный текст.
2. Добавить настройки в `AuthProperties` или в отдельный `SmsProperties`, например
   `app.sms.provider`, `app.sms.api-key`, `app.sms.sender`. Переменные окружения:
   `APP_SMS_PROVIDER`, `APP_SMS_API_KEY`, `APP_SMS_SENDER`.
3. В `AuthConfig.otpSender()` перед `UnavailableOtpSender` вернуть новый отправитель,
   если провайдер настроен:
   ```java
   if ("smsru".equals(sms.provider())) return new SmsRuOtpSender(sms, restClientBuilder);
   ```
4. Тест: фальшивый HTTP-сервер (как `PushStub` в тестах), чтобы проверить, что запрос уходит с нужным номером
   и что ответ с ошибкой превращается в 503.
5. На сервере дописать `APP_SMS_*` в `/opt/dating/.env` и перезапустить установку. Тестовые номера продолжат
   работать с фиксированным кодом, остальные будут получать SMS.

### Выбор оператора

| Вариант | Плюсы | Учесть |
|---|---|---|
| SMS-агрегатор (SMS.ru, SMSC, SMS Aero, МТС Exolve и т. п.) | простой HTTP API, оплата по факту | буквенное имя отправителя регистрируется у операторов связи, это занимает дни |
| Код звонком (flash call, последние цифры номера) | заметно дешевле SMS | надо поменять тексты: «введите последние 4 цифры номера» |
| Telegram Gateway | дёшево | есть не у всех; держать SMS запасным вариантом |

Перед запуском проверь в договоре: защита от SMS-флуда (фрод с дорогими направлениями), ограничение стран
(только +7, если не нужны другие) и отчёты о доставке.

## 2. Оплата

### Что уже есть

- Выдача вещей: `EconomyService.grant(accountId, source, sourceRef, idempotencyKey, rewards)`.
  - Для покупок `source = RewardSource.PURCHASE`, ключ `purchase:<orderId>`.
  - Для подписки `RewardSource.SUBSCRIPTION`, ключ `subscription:<id>:<period>`.
  - Повтор с тем же ключом ничего не делает, поэтому повторный вебхук безопасен.
- Награды: `Reward.Item(code, qty)` (суперлайки, бусты, билеты, косметика) и `Reward.PremiumDays(n)`.
- Возвраты: источник `RewardSource.REFUND` для обратной операции.
- Чего нет: товаров с ценами, заказов, платёжных эндпоинтов.

### Что добавить в бэкенд (модуль `payments`)

1. **Миграции.**
   - `products`: код, название, цена в копейках, валюта, награды (JSON в формате `Reward`), активен ли.
   - `orders`: id, аккаунт, товар, сумма, статус `NEW`/`PAID`/`CANCELED`/`REFUNDED`, провайдер,
     id платежа у провайдера, даты.
2. **API.**
   - `GET /shop/products` — витрина.
   - `POST /orders {productCode, idempotencyKey}` — создаёт заказ и платёж у провайдера, возвращает
     `confirmationUrl` (веб) или данные для SDK (приложение).
   - `POST /payments/webhook/{provider}` — **единственное место**, где заказ становится оплаченным.
3. **Обработка вебхука.**
   - Проверить подлинность: подпись или секрет провайдера и/или его IP. Затем перепроверить статус
     платежа запросом к API провайдера.
   - Сверить сумму с заказом.
   - В одной транзакции: `orders.status = PAID` и `economyService.grant(..., "purchase:" + orderId, rewards)`.
   - Ответить 200 даже на повтор. Ключ идемпотентности не даст выдать дважды.
4. **Нельзя выдавать по сигналу от клиента** («оплата прошла» из приложения): только по вебхуку или после
   проверки чека на сервере.
5. **Возврат.** Вебхук refund: заказ получает статус `REFUNDED`, расходники списываются с `RewardSource.REFUND`.
   Что делать, если их уже потратили, решаешь ты; обычно баланс просто уходит в ноль.

### Где принимать деньги

| Канал | Чем | Важно |
|---|---|---|
| Веб | ЮKassa, CloudPayments, Т-Касса | нужны ИП/ООО и онлайн-касса по 54-ФЗ: у ЮKassa и CloudPayments есть встроенные чеки; для подписки нужны рекуррентные платежи (сохранённая карта) |
| Android через Google Play | Google Play Billing | цифровые товары в приложении из Google Play продаются только через их биллинг; чек (purchase token) проверяется на сервере через Google Play Developer API, покупку нужно подтвердить (acknowledge) |
| Android через RuStore | RuStore Pay SDK | проверка покупки на сервере через API RuStore; актуальные правила о сторонних платёжках смотри в правилах RuStore |
| APK напрямую (как сейчас) | веб-оплата в браузере | приложение открывает `confirmationUrl`, после оплаты возвращается по deep link и перечитывает кошелёк |

### Платная гача

Если билеты гачи будут продаваться за деньги:
- заведи отдельный код `GACHA_TICKET_PAID` (у баннера уже есть `costItemCode`);
- держи шансы раскрытыми (API уже отдаёт `rates`);
- проверь требования сторов и закона к платному рандому, включая возрастные ограничения и лимиты трат.

### Порядок работ

1. Определиться с юрлицом и провайдером, получить тестовый магазин (sandbox).
2. Таблицы и витрина: `products` и `GET /shop/products`.
3. Заказ и вебхук в режиме sandbox, интеграционный тест с фальшивым провайдером: заказ → вебхук →
   кошелёк пополнен; повтор вебхука ничего не меняет; неверная подпись → 401.
4. Экран «Магазин» в вебе и мобилке, возврат после оплаты.
5. Боевые ключи провайдера в `.env` на сервере (`APP_PAYMENTS_*`), адрес вебхука
   `https://instareject.ru/api/v1/payments/webhook/<provider>` в кабинете провайдера.
